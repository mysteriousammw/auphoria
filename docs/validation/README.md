# Validation

AUPHORIA guards against two errors: analyses producing the *wrong number*, and
analyses quietly doing the *wrong thing*. This folder records the maturity of
every analysis, the independent reference it is cross-checked against, and any
known issues.

## Quick view

- **Maturity levels** — `levels.md`: `experimental`, `tested`, `reviewed`,
  `validated`. The build agent may set only `experimental` or `tested`;
  `reviewed` and `validated` require a named human reviewer in the manifest's
  `reviewer` field (enforced — see below).
- **Dashboard** — `dashboard.md`: generated automatically, one row per
  analysis (maturity, reviewer, reference, tests, known issues). **Do not edit
  it by hand.**
- **Reference values** — `references.yaml`: for every analysis, the
  independent reference `source`, `how_produced`, and the exact expected
  `values` with tolerances. These come from hand-computed textbook examples and
  second-library reproduction (scikit-learn / statsmodels / SciPy). R is not a
  runtime dependency, so an R call is not used.
- **Known issues** — `KNOWN_ISSUES.md`: outstanding problems, grouped per
  analysis.
- **Issue template** — `.github/ISSUE_TEMPLATE/wrong_result.md`: for reporting
  an analysis that does not match an independent reference.

## Regenerating the dashboard

The dashboard is generated by a script; never edit `dashboard.md` directly.

```
python scripts/gen_validation_dashboard.py        # write dashboard.md
python scripts/gen_validation_dashboard.py --check  # verify it is current
auphoria validation                                # same as the first line
```

The script also ENFORCES the maturity rules: a manifest claiming `reviewed` or
`validated` without both a `reviewer` and a `reference` fails with a non-zero
exit code (and is rejected at analysis load time by
`core/manifest.py::validate_maturity`).

## Maturity policy

- **Nothing is ever labelled `validated`** by the build agent. All analyses
  ship `experimental` or `tested`.
- Automated known-answer tests are the floor: every analysis passes tests with
  small synthetic data and expected values (hand-computed, or from a
  documented reference example).
- Promotion to `reviewed` or `validated` happens only after a real validation
  record exists *and* a named human reviewer is recorded in the manifest. The
  reviewer gate fails a check until then.

## Adding a validation exercise

For a new cross-check:

1. Put the expected values and how they were produced in
   `docs/validation/references.yaml` under that analysis id.
2. Add the known-answer test / reference in the analysis's `tests/`.
3. Re-run the dashboard generator.

See `references.yaml` for the format.
